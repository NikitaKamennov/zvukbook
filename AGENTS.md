# Zvukbook — «Звуккниг»

Отдельный проект локальной подготовки русскоязычных аудиокниг. Общаться на русском, на «ты», понятно объяснять причины решений.

## Назначение и устройство

- Текст книг не отправлять во внешние сервисы. OCR — Tesseract rus; синтез — локальная Silero v5_6_ru через PyTorch CUDA.
- Flask/SQLite, один обработчик, MP3 по главам. У главы один текущий MP3; успешная переозвучка заменяет его. Правка отдельной главы не сбрасывает готовность остальных.
- Код — `book_renderer/`, вход — `zvukbook.py`, запуск — `bash scripts/start-local.sh`, страница — `http://127.0.0.1:8767/`.
- Окружение, модель и библиотека — `.local-data/books-renderer/`. Там же находятся личные книги, MP3 и SQLite; не коммитить их и не читать содержимое ради знакомства с архитектурой. Для адресной диагностики нужен запрос владельца.
- Канонические схемы `projectpro-local-book-v1` и `projectpro-audiobook-v2` унаследованы от исходного приложения; сохранять совместимость существующих данных при переименовании проекта.
- Начинать с `README.md`; пользовательские сценарии — `docs/books-start.md`, Windows-сборка — `docs/windows-build.md`, публикация — `docs/github-publication.md`.
- В рабочей копии владельца могут присутствовать игнорируемые планы, handoff и журналы в `docs/`. Читать их по необходимости, если файлы есть; публичная копия проекта не требует их наличия.

## Обязательные режимы работы

- Сохранять Linux-лабораторию: `bash scripts/start-local.sh` и локальная страница для экспериментов с Python/моделями. Запуск исходного сервера не должен требовать сборки Go/Wails/EXE или Windows-компонентов.
- Windows desktop получает отдельные настройки, зависимости, runtime и сборку; общее Python-ядро и пользовательские сценарии глав сохраняются. Linux cgroup/bubblewrap остаются в своём адаптере, Windows-защиты реализуются отдельно.
- Не пересоздавать Linux `.local-data/books-renderer/.venv` из Windows и не устанавливать туда Windows-пакеты. Для Windows использовать отдельное окружение. Первые опыты проводить с вымышленными текстами и отдельной библиотекой.
- Смена модели в лаборатории должна оставаться конфигурацией/адаптером и перезапуском исходного сервера; она не требует пересборки desktop. Новые параметры конфигурации вводить явно, не описывать ещё не реализованные команды как действующие.

## Правила изменений и проверки

- Делать только необходимые изменения. Не менять соседний ProjectPro и другие проекты без отдельного поручения.
- При изменении функций, кнопок или пользовательских сценариев проверять и в том же изменении актуализировать встроенную справку и подсказки интерфейса, а также затронутые инструкции в README и docs. Не описывать ещё не реализованное поведение как работающее.
- **Не запускать автоматические тесты, проверки синтаксиса, браузерные/smoke-проверки, сервер, OCR или синтез для проверки изменений без отдельного явного запроса.** Владелец выбрал ручную проверку. В итоге указывать, что фактически запускалось, а что осталось непроверенным.
- Сохранять квоты cgroup, проверки свободной RAM/VRAM/диска, одну задачу за раз, отмену и изоляцию bubblewrap. Не включать обход sandbox, CPU fallback, автоматическое повышение лимитов или бесконечные повторы после ошибки.
- Не читать `.env`, ключи и чужие данные. Не коммитить и не публиковать личные книги, логи или результаты без запроса.
- На текущем этапе приложение работает только локально. Удалённые установки, деплой и изменения Nginx/PM2 требуют отдельной задачи; архивный серверный план не даёт разрешения на них.
- GitHub содержит исходники, инструкции, конфиги/lock и лицензии. Установщики, portable, runtime, модель и личные данные не публиковать. Пользователь собирает приложение локально по README.
- Собственный код — MIT; модель и зависимости имеют отдельные лицензии. Сохранять их уведомления и SHA manifest; не распространять MIT приложения на веса Silero.
